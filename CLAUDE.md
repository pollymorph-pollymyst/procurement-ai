# Планирование закупок — инструкции для Claude Code

Система для импортёра электроинструмента, садовой техники и сантехники из Китая (поставка 4–6 месяцев).
По выгрузке из ERP считает: что и сколько заказать, на сколько хватит запаса с учётом заказов в пути,
когда размещать следующий заказ, где риск дефицита или избытка. Результат — дашборд `docs/index.html`
и Excel-заказы по поставщикам в `docs/orders/`.

Пользователь — закупщик, не программист. Всё, что он видит, — на простом русском, без слов
«модель», «ИИ», «LLM», «алгоритм», «SKU». Термины — из `GLOSSARY.md`.

## Как устроено

```
Входящие/            ← папка с выгрузками по умолчанию (xlsx/csv/zip из 1С и др.); можно сменить в «Управлении»
data/raw/            ← 6 CSV выгрузки (описание полей — data/raw/README.md)
config.toml          ← все настройки на русском (наценка, сроки, уровень сервиса, …)
procurement/
  sources.py         ← приём выгрузок: распознавание файлов и колонок, mapping.json, outputs/intake.json
  data.py            ← чтение и проверка CSV из data/raw, truncate() для проверки на прошлом
  holidays.py        ← праздники у поставщиков → удлинение срока (разделы «праздник …» в config.toml)
  writers.py         ← кто пишет комментарий: claude / openai-совместимый / gigachat / local / нет; ключи в .env
  server.py control.py settings.py schedule.py ← панель «Управление» (python -m procurement serve)
  forecast.py        ← спрос: месяцы без остатка исключаются, сезонность категории, уровень, тренд
  plan.py            ← дневная симуляция запаса, страховой запас, дата и количество заказа, статусы
  pipeline.py        ← собирает всё в result (KPI, заказы по поставщикам, риски, календарь, карточки)
  backtest.py        ← проверка точности прогноза на прошлом годе против «среднего за год»
  history.py         ← снимки каждого запуска и разница «что изменилось»
  commentary.py      ← «Комментарий аналитика»: шаблон / выбранный сервис (writers.py) / Claude Code + проверка чисел
  export.py          ← Excel по поставщикам, общий Excel и CSV
  build.py           ← вставляет данные в dashboard/index.html → docs/index.html; zip для отправки
dashboard/index.html ← шаблон дашборда (vanilla JS + SVG). Правим ТОЛЬКО его, docs/index.html — сборка
prompts/analyst.md   ← промпт «Комментария аналитика» (общий для API и для скилла)
outputs/latest/      ← result.json и facts.json последнего расчёта
outputs/history/     ← снимки запусков для раздела «Что изменилось»
tests/               ← pytest
.claude/skills/      ← plan-purchases, explain-sku
```

## Команды

```bash
python -m procurement serve             # дашборд с панелью «Управление» на 127.0.0.1
python -m procurement run --no-open     # полный расчёт (~6 с): заказы, Excel, дашборд, снимок
python -m procurement check             # только проверить данные и показать KPI
python -m procurement comment           # вставить outputs/commentary_override.json без пересчёта
python -m procurement sku SKU-F4FE31    # расчёт по одному артикулу
python -m procurement package           # zip проекта в dist/
python -m pytest -q                     # тесты (pip install -r requirements-dev.txt)
```

На Windows перед запуском из терминала: `set PYTHONIOENCODING=utf-8` (иначе кириллица в консоли ломается).
Пользователь запускает всё двойным щелчком: «Обновить анализ.bat».

## Правила

- **Числа не придумываем.** Любое число в комментарии или объяснении берётся из `outputs/latest/facts.json`
  или `python -m procurement sku`. `commentary.check_numbers` отбрасывает текст с чужими числами.
- Логику расчёта меняем в `procurement/`, пороги — в `config.toml` (новый ключ → `_MAP` в `config.py`).
- Первая настройка (мастер в дашборде): `config.toml` → `["установка"] "пройдена"`. "нет" — мастер откроется
  при следующем открытии; `sources.preview` только читает папку, `/api/setup/done` ставит "да" и запускает расчёт.
- После правки `dashboard/index.html` пересобрать: `python -m procurement comment` (быстро) или `run`.
- Решения, принятые с заказчиком: дата анализа = дата выгрузки; цикл заказа 30–90 дней по поставщику;
  сервис A 95% / B 90% / C 85%; заказы в пути, просроченные > 60 дней, в запас не входят;
  наценка < 25%, «нужен поставщик» и редкий спрос — отдельные списки, не в заказ; избыток — запас > 12 мес.;
  заказы в пути × доля довоза поставщика (≥ 3 закрытых заказов, не ниже 30%); праздники удлиняют срок;
  «Отправлено» в дашборде = заказ в пути до следующей выгрузки (outputs/sent_orders.json);
  «Не успеем довезти» — и у товаров с заказом в пути, если до его прихода склад пуст (поле gap_until),
  но только если упустим хотя бы 1 шт.; файл поставщику (`export.SUPPLIER_COLS`) — без внутренних колонок,
  пустые колонки не выводятся; выключатель автообновления не меняет daily.yml.
- Приём выгрузок: продажи/остатки сливаются по месяцам с прошлой выгрузкой; при признаках неполноты
  (товаров < 50% прошлого, > 50% артикулов не из справочника) — IntakeError, «Взять как есть» → outputs/intake_accept.json.
  Дата выгрузки (`sources._export_date`): имя файла → дата файла, но не позже конца последнего месяца в данных + 7 дн.
- Ключи сервисов — только в `.env`. Никогда не писать их в config.toml, дашборд, логи или ответы.
- Не коммитить и не публиковать без явной просьбы пользователя.
